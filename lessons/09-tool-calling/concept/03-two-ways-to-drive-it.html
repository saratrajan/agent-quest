How does the model's text become a structured tool call? There are two routes, and you will use both in the first experiment.

Native tool calling. Most current models were trained on conversations that include tool descriptions and calls in a fixed text format. The software that runs the model (here, Ollama) writes your descriptions into the prompt in that format, and parses the model's output back into a tool_calls list. You pass tools= and get structure back. This is what you would normally use.

Constrained output. Session 5 showed that the next token is drawn from a distribution, and that tokens can be filtered before the draw. The same trick can force valid structure: at each step, allow only tokens that keep the output a valid instance of a schema you supply. Describe the tools in the instructions, constrain the reply to {"thought": ..., "tool": ..., "arguments": ...}, and the model cannot produce a malformed call or name a tool that does not exist. The given function agentkit.step does this, then converts the reply into the same message shape native calling produces, so your loop works with either.

Both routes made the same calls and reached the same answer. The native route was eight times slower on the second question because this model reasons at length before each turn: 2,235 tokens of private reasoning to decide on one lookup. The constrained route asks for the reasoning as a one- or two-sentence thought inside the reply. That pattern, a brief stated thought followed by one action, is the ReAct pattern, and the thought also makes the trace readable, which you will rely on in session 10.

Neither route is always right. Long reasoning sometimes finds what a short thought misses, and a different model may reason far less. The point is that the route is a choice, with a measurable cost, and you now know what is underneath both.

What goes wrong. Three failures from the last experiment, each with a general lesson:

  • A result misread. Asked for the exact number of payments incidents last year, the model searched for the word "payments", got back "22 matching", and answered "22". The tool counted keyword matches across all time; the model reported it as the answer to a different question. A tool's output must say what it is, and some questions should be refused.
  • A gap in the tools. Asked which runbook applies after a bad deploy, the model looked up the cruises service, found no runbooks listed, and said none exists. One does: the rollback runbook is filed under another service. An agent can only find what its tools can reach.
  • No way to stop. Given a tool that always says "check again", the model obeyed until the turn limit ended the run.
